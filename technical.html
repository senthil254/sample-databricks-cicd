Not Git folders. Two ways exist to join GitHub and Databricks. Git folders clone the repo into the workspace — you edit notebooks there. Asset Bundles (this guide) make GitHub the source of truth and push deployments in. Nothing is cloned into the workspace here.

Before you start

Check the account. One workspace URL belongs to exactly one Databricks account. During this build a service principal was created in the wrong workspace — its credentials simply cannot authenticate to another account. Always confirm the host in the browser address bar.

Step 2

Create a service principal

This is the identity CI uses. It is not a person.

  • Workspace Settings
  • Identity and access → Service principals
  • Add one, then Generate secret

You get two values:

  • Client ID — an identifier, not sensitive
  • Secret — sensitive, shown once

Copy the secret immediately. It is never shown again. If you lose it, generate a new one.

Check it works

Both were measured, not assumed. A PAT against the account API returns 401 — Credential was not sent or was of an unsupported type. Expiry was near-identical (729 vs 730 days), so rotation effort is not a deciding factor. Use M2M for CI; a PAT is fine for a single-workspace demo.

Step 4

Configure the bundle

file · databricks.yml
bundle:
  name: databricks-cicd-demo

include:
  - resources/*.yml

workspace:
  host: https://dbc-f818cfa1-b8d3.cloud.databricks.com

targets:
  dev:
    default: true
    mode: development
    workspace:
      root_path: /Workspace/Users/${workspace.current_user.userName}/.bundle/${bundle.name}/${bundle.target}

  prod:
    mode: production
    workspace:
      root_path: /Workspace/Users/${workspace.current_user.userName}/.bundle/${bundle.name}/${bundle.target}

Why ${workspace.current_user.userName}? It resolves to whoever deploys — you locally, the service principal in CI. A hardcoded email breaks the moment CI runs as a different identity.

Step 6

Set the GitHub secrets

Three are needed:

  • DATABRICKS_HOST
  • DATABRICKS_CLIENT_ID
  • DATABRICKS_CLIENT_SECRET
cli · in
gh secret set DATABRICKS_HOST -R OWNER/REPO --body "https://dbc-f818cfa1-b8d3.cloud.databricks.com"
gh secret set DATABRICKS_CLIENT_ID -R OWNER/REPO --body "93bf11e8-964d-4b9b-8989-f14234f2b6f9"
printf '%s' 'YOUR_SECRET' | gh secret set DATABRICKS_CLIENT_SECRET -R OWNER/REPO

Use printf, not echo. echo appends a newline, and a newline inside the secret is enough to break authentication. This cost two failed runs during this build.

cli · in
gh secret list -R OWNER/REPO

A listed secret is not a working secret. gh secret list only proves the name exists. An empty or malformed value looks identical here. Only a pipeline run proves the value.

Step 7

The workflow

What triggers what

TriggerTargetDeploysRuns job
Pull requestdevno — validate onlyno
Push to maindevyesno
Push tag v*prodyesno
Actions buttonyour choiceyesonly if ticked
file · .github/workflows/ci-cd.yml (triggers)
on:
  workflow_dispatch:
    inputs:
      target:
        description: Bundle target to deploy
        type: choice
        options: [dev, prod]
        default: dev
      run_job:
        description: Also run the job after deploying
        type: boolean
        default: false
  push:
    branches: [main]     # -> dev
    tags: ['v*']         # -> prod
  pull_request:          # -> tests only
file · ci-cd.yml (target choice)
- name: Decide target
  id: t
  run: |
    if [[ "${GITHUB_REF}" == refs/tags/v* ]]; then
      echo "target=prod" >> "$GITHUB_OUTPUT"
    elif [[ "${{ github.event_name }}" == "workflow_dispatch" ]]; then
      echo "target=${{ inputs.target }}" >> "$GITHUB_OUTPUT"
    else
      echo "target=dev" >> "$GITHUB_OUTPUT"
    fi

Why the job does not run on every push. One commit here only added a workflow trigger — no notebook, no logic change — yet it executed a real job on paid compute. Deploying proves the job is installed correctly; running it costs money and touches data. So running is opt-in.

Pin your actions

file · ci-cd.yml
uses: actions/checkout@v5
uses: actions/setup-python@v6
uses: databricks/setup-cli@v1.17.0

Tracking @main lets an upstream change break CI with no commit of your own.

Troubleshooting

"cannot configure default credentials"

This message is misleading. It sounds like nothing was supplied — but the credentials are present and wrong.

cli · out
Error: failed during request visitor: default auth: cannot configure
default credentials ... Config: host=***, client_id=***, client_secret=***

The SDK tries the OAuth exchange, the server rejects it, and the whole chain is reported as unconfigurable. The real invalid_client answer never surfaces.

Usual cause: a trailing newline in the secret. Re-set it with printf.

Secret exists but CI still fails

Check the run log. GitHub masks real values as ***; an empty value shows as nothing at all:

cli · out
DATABRICKS_HOST: ***
DATABRICKS_CLIENT_ID: ***
DATABRICKS_CLIENT_SECRET:          <- empty

The CLI also lists what it found: Env: DATABRICKS_HOST, DATABRICKS_CLIENT_ID — two, not three.

"refresh token is invalid"

That profile uses OAuth U2M (user-to-machine), which needs a browser login that has expired. It is not M2M. Re-authenticate:

cli · in
databricks auth login --host <workspace-url> --profile <name>
"src refspec v0.1.0 does not match any"

The tag does not exist locally. Create it, then push — as two steps.

cli · in
git tag v0.1.0
git push origin v0.1.0
Bundle deploys but the job will not run

Check the workspace compute mode. A serverless-only workspace cannot start classic job clusters — but a plain notebook task needs no compute block at all.
