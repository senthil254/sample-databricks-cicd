Why

The problem we solved

Databricks is where the data work happens. The code for that work lives in GitHub.

Moving code from one to the other by hand is slow and risky:

  • Someone copies the wrong version
  • Someone forgets a step
  • Nobody is sure what is running right now
  • A broken change reaches production unnoticed

In one line: we made the move automatic, repeatable, and checked at every step.

What

What we built

A pipeline. Think of it as a delivery line with inspection points.

  • A developer saves their work to GitHub
  • Tests run automatically
  • If tests fail, nothing is delivered
  • If tests pass, the work is installed into Databricks

Two separate destinations

NameWhat it is forWho it affects
devPractice area. Try things safelyJust the developer
prodThe real thingEveryone

Getting to prod requires a deliberate act — a release marker, or a button someone chooses to press. It never happens by accident.

How

How it flows

Two different things — worth separating

ActionMeaningCosts money?

We deploy often. We run only when we mean to.

Safety

The safety rails

RailWhat it prevents
Tests run firstBroken code being delivered
Proposals are tested, never deployedUnreviewed work reaching anything real
dev and prod are separateExperiments touching live data
Passwords stored in a vaultSecrets sitting in readable files
A robot account, not a person’sEverything breaking when someone leaves

The robot account matters more than it sounds. If the pipeline used a person’s login, their holiday, password change, or departure would stop deliveries. A dedicated non-human account has no such life events.

Money

What this costs

  • Storing the code — free
  • Running the tests — free for this size
  • Installing into Databricks — free
  • Running the actual job — this is the part that costs

A real example from this build

One change touched only a settings file. No data logic at all. Yet it started a real job on paid machines — simply because the old setup ran the job on every save.

We changed that. Saving now installs the work but does not run it. Running is a deliberate choice. Small sum here; the same pattern on a large pipeline is a real bill.

Honesty

What went wrong along the way

Three things, all worth knowing:

1. A password saved as blank

  • An automated helper saved the password — but saved nothing
  • The system showed the password as existing
  • It only failed when the pipeline actually ran

Lesson: a listed password is not a working password. Only a real run proves it.

2. One invisible character

  • Second attempt saved the password with an extra invisible line-break
  • Everything looked correct
  • Login failed anyway

Lesson: the error message blamed “missing credentials” when the credential was present and merely wrong. Misleading errors cost time.

3. The right key, the wrong building

  • A robot account was created — in the wrong Databricks account
  • Its credentials were valid, just for somewhere else

Lesson: check which account you are in before trusting a credential.
